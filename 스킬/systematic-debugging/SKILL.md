# 원인부터 찾는 디버깅

원인을 확인하기 전에는 코드를 고치지 않는다. 짐작으로 여러 군데를 한꺼번에 바꾸지 않는다.

1. 재현: 실패하는 명령을 run으로 그대로 실행하고 오류 전문을 읽는다(첫 오류 줄, 파일 이름, 줄 번호).
2. 범위 좁히기:
   - 오류가 가리키는 파일의 그 줄 앞뒤를 read로 읽는다.
   - 최근 변경을 본다: run text=`git status --short; git diff --stat` (git 저장소일 때).
   - 같은 일을 하는데 잘 되는 코드가 있으면 read로 읽어 다른 점을 찾는다.
3. 가설 하나: "<원인> 때문에 <증상>이 생긴다"를 한 문장으로 정한다. 값을 출력하는 한 줄을 넣거나 작은 입력으로 run 해서 가설이 맞는지 먼저 확인한다.
4. 수정 하나: 원인 한 곳만 edit로 고친다. 확인용으로 넣은 출력 줄은 지운다.
5. 검증: 1번 명령을 다시 run 해서 통과를 보고, 원래 되던 인접 기능도 한 번 실행한다.

규칙:
- 가설이 틀리면 방금 고친 줄만 edit로 원래대로 되돌리고, 새 가설을 한 문장으로 다시 세운다. 수정 위에 수정을 쌓지 않는다. git checkout, git reset 으로 되돌리지 않는다(다른 작업까지 사라진다).
- 수정이 3번 실패하면 멈추고 보고한다: 재현 명령, 확인한 사실, 틀린 가설, 남은 의심.
- 계획 실행 중에 불려 왔으면, 고친 뒤 plan의 남은 단계로 돌아간다.
- 오류 메시지를 숨기는 수정(빈 catch, 테스트 삭제, 검사 끄기)은 하지 않는다.

재현 조건을 이미 아는 회귀는 debug-regression 스킬이 더 짧다.
